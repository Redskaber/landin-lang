## 1. Problem Statement

When `fn process<T: Clone>(x: T) { x.clone() }` is monomorphized to
`process<i32>`, the `x.clone()` Call terminator's func operand still
points to the trait declaration method (no body), not the concrete impl
method `landin_i32_clone`. The generated IR produces `call @null(ptr)`
which crashes at runtime.

### Root Cause

1. **MIR lowering** (`resolve_trait_method` for `Param(N)` receiver):
   Returns the trait declaration's method DefId (no body). This is
   correct at lowering time — the concrete type isn't known yet.

2. **Monomorphization** (`substitute_mir_body`):
   Substitutes `Param(N)` types with concrete types in local_decls and
   operand types. But does NOT re-resolve Call terminator func operands
   — they still point to the trait declaration method.

3. **Codegen** (`codegen_mono_functions`):
   Emits the specialized MIR body with the stale func operand → `@null`.

### Why It's P1

`impl Trait` args are unusable for method calls inside the body — the
most common use case. `fn process(x: impl Clone) { x.clone() }` compiles
but crashes at runtime.

---

## 2. Design: Pre-computed Trait Method Resolution Map

Per §16 (codegen is HIR-free), the trait method resolution must be
pre-computed in the driver (before codegen) and passed as data.

### 2.1 New Data Structure: `TraitMethodResolutionMap`

```rust
/// Maps a (trait_method_def_id, concrete_type) pair to the concrete
/// impl method's DefId. Built by the driver after trait resolution,
/// before codegen.
///
/// Example: (Clone::clone DefId, i32) → i32::clone impl DefId
pub struct TraitMethodResolutionMap {
    /// Key: (trait_method_def_id, type_name_string)
    /// Value: concrete impl method DefId
    map: HashMap<(DefId, String), DefId>,
}
```

### 2.2 Driver: Build the Map (new pass)

After trait_resolver is built, before codegen:
1. For each trait method in the HIR
2. For each concrete type that implements that trait
3. Map (trait_method_def_id, type_name) → impl_method_def_id

### 2.3 Codegen: Re-resolve in codegen_mono_functions

In `codegen_mono_functions`, after `substitute_mir_body`:
1. Walk the specialized MIR body
2. For each `Call { func, .. }` terminator:
   - If func is `Constant(FnDef(trait_method_def_id, []))`
   - Look up the receiver type (from the first arg's local_decl)
   - If the receiver type is now concrete (not Param/Infer)
   - Look up `(trait_method_def_id, type_name)` in the map
   - Replace the func operand with the concrete impl method

### 2.4 Implementation Steps

| Step | Description | Effort |
|------|-------------|--------|
| 1 | Define `TraitMethodResolutionMap` in `src/mir/monomorphize/mod.rs` | 1 hour |
| 2 | Build the map in driver (new function in `driver_codegen_prep.rs`) | 2 hours |
| 3 | Thread the map through `codegen_mono_functions` | 1 hour |
| 4 | Re-resolve Call terminators in specialized MIR bodies | 3 hours |
| 5 | Tests (positive: `impl Clone` method call works; negative: wrong type) | 2 hours |
| **Total** | | **~9 hours** |

## 3. Alternative Approaches Considered

### 3.1 Approach A: HIR in Codegen (REJECTED)

Thread HIR + trait_resolver into `codegen_mono_functions`.
- **Pros**: Direct access to trait resolution
- **Cons**: Violates §16 (codegen is HIR-free). Major design boundary violation.
- **Status**: REJECTED per §16

### 3.2 Approach B: Metadata on Call Terminator (REJECTED)

Store `Param(N)` index + method name as metadata on the Call terminator
during MIR lowering. During monomorphization, use this metadata.
- **Pros**: No HIR in codegen
- **Cons**: Requires changing `TerminatorKind::Call` (adds fields). Breaks
  all pattern matches on Call. Large refactor.
- **Status**: REJECTED — too invasive

### 3.3 Approach C: Pre-computed Map (CHOSEN)

Pre-compute `(trait_method_def_id, type_name) → impl_method_def_id` map
in the driver. Pass as data to codegen.
- **Pros**: No HIR in codegen (per §16). Minimal MIR changes. Rustc-style.
- **Cons**: Requires a new driver pass. Need to handle all concrete types.
- **Status**: CHOSEN — correct design boundary, minimal scope

## 4. Test Plan

### Positive Tests
1. `fn process(x: impl Clone) -> i32 { let _y = x.clone(); 42 }` — method call works
2. `fn process(x: impl Display) { let mut s = String::new(); x.fmt(&mut s); }` — Display method works
3. Multiple `impl Trait` args with method calls

### Negative Tests
1. `impl Trait` with method that doesn't exist → error
2. `impl Trait` arg with type that doesn't implement the trait → error (TD-IMPL-TRAIT-CALLSITE-CHECK)
