## 3. 时机评估

### 3.1 ✅ 支持的方面

- **HIR/MIR 结构稳定性**: 足够稳定, 可用作缓存键
- **DefId 稳定性**: 足够稳定, 可标识 item
- **编译管道隔离**: §16 合规, 各阶段数据流清晰

### 3.2 ❌ 不支持的方面

- **单文件限制**: 当前 `compile(src: &str)` 只接受单文件源码,
  增量编译需要知道哪些 item 变了 — 这需要文件系统级别跟踪
- **无项目系统**: 没有 `Cargo.toml` 或项目文件, 无法确定编译单元
- **Param unify**: 泛型类型推断不稳定, 同一输入可能产生不同 MIR
- **无序列化**: MIR 不可序列化到磁盘, 无法持久化缓存

### 3.3 🟡 部分支持但需改进

- **依赖图**: 可以基于 HIR 分析 item 间依赖, 但当前无实现
- **MIR hash**: 可以对 MIR 做 hash, 但 MIR 包含 `Span` 等不稳定信息

## 4. 评估结论

### ❌ 当前不适合实现增量编译

**理由**:

1. **单文件编译是根本限制**: 增量编译的核心价值是 "只重编译变更的 items",
   但当前编译器只接受单文件输入 — 无法跟踪哪些 items 变了。
   需要 v0.2 项目系统 (mini-cargo) 才有意义。

2. **Param unify 不安全**: 泛型代码的类型推断结果不稳定,
   导致 MIR hash 不稳定, 缓存命中率低。
   需要 v0.2 单态化基础设施。

3. **用户此前要求移除**: Stage 18.83 用户明确要求移除增量编译内容,
   理由是 "当前不需要, 而且存在干扰, 并且还未到稳定版本"。
   当前项目仍是 v0.1 阶段, 未到稳定版本。

4. **ROI 低**: 增量编译需要 4-6 stages 实现 (依赖图 + 缓存键 +
   增量重建 + 测试), 但当前编译速度足够快 (单文件 < 1s),
   投入产出比不高。

### ✅ 纳入 v0.2 规划

增量编译应作为 **v0.2 路线图** 的一部分, 在以下前置条件满足后实施:

1. **v0.2 单态化完成** — 解决 Param unify 不安全
2. **v0.2 项目系统 (mini-cargo)** — 支持多文件/项目编译
3. **v0.2 MIR 序列化** — 支持 MIR 持久化到磁盘
4. **v0.2 crate 图** — 支持 crate 间依赖跟踪

## 5. v0.2 增量编译路线图 (规划)
