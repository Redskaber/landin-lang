# 00 — 项目需求历程与变更记录

> 本文档记录 Landin 语言项目的所有用户需求变动、决策响应、版本演化。每次需求变动都需阅读本文档并追加记录。

---

## 1. 需求历程时间线

### 需求 #1（2026-07-18，模拟时间）：编译器知识 + 自举能力

**用户需求**：
> 关于编译器相关的知识，你当前截至时间是在什么时候的知识，你是否能够在思考-设计-实现-测试-报告-修正这条正向循环中完整完全的从 0 设计实现一门底层编程语言的能力并使用真实环境或虚拟机进行测试。

**AI 响应**：

- 声明知识截止到 2024-2025 初
- 确认具备完整闭环能力（思考-设计-实现-测试-报告-修正）
- 提出 4 种落地路径供选择

**决策**：用户未立即选择，继续追问前沿方向

---

### 需求 #2（2026-07-18）：编译器前沿方向

**用户需求**：
> 截至2026-07 当前编译器前沿方向和发展，设计推荐方向等

**AI 响应**：

- 列举 11 个前沿方向（ML for Compilers / MLIR / WASM GC / Rust 演化 / eBPF / Effect Systems / 形式化验证 / LLM-native / 异构编译 / Security-aware / JIT 复兴）
- 推荐 4 个技术栈组合（A: MLIR+WASM / B: LLVM+C-like / C: eBPF+WASM / D: Research）

**决策**：用户选择"类似 Rust MVP 自举"

---

### 需求 #3（2026-07-18）：Rust-like MVP 自举所需

**用户需求**：
> 设计实现 类似rust mvp 自举需要哪些

**AI 响应**：

- 列出自举所需完整清单：语言子集 / 编译器 pipeline / 自举策略 / 工具链 / 标准库 / 规模估算
- 提出 6 个需立即决策的问题
- 推荐宿主语言 Rust / LLVM only / NLL / monomorphization

**决策**：用户说"决策根据你的推荐即可"，启动多 Agent 团队深度研究

---

### 需求 #4（2026-07-18，第 1 次）：多 Agent 深度研究 + 蓝图设计

**用户需求**：
> 在多agent group 团队协作深度思考和查阅 rust 官方仓库和对应最自举前仓库，深度深入查阅编译器设计相关书籍和编译原理；对其进行多轮反复审查迭代打磨最初语言的蓝图（标准编译器文档集合），相互印证，查漏补缺为真正的设计和实现做好准备（仅当基本无可挑剔，内容覆盖完整，完整文档集合收敛为止，此次为审查文档集合的最后阶段）。

**AI 响应**（第 1 轮研究 R1-R4）：

- 4 个并行研究 Agent：R1 Rust 自举史 / R2 rustc 架构 / R3 编译原理 / R4 可比语言
- 产出 v1.0 蓝图：13 个文档，7,455 行
- 语言定名 **Forge**

**决策**：v1.0 完成，但用户要求继续审查

---

### 需求 #5-#10（2026-07-18，第 2-7 次）：反复审查迭代

**用户需求**（重复 6 次）：
> 同上"多轮反复审查迭代打磨...仅当基本无可挑剔..."

**AI 响应**（第 2-6 轮审查 R5-R23）：

- R5-R9：发现 7 soundness 漏洞 / 25 rustc 遗漏 / 10 引用错误 / 工作量低估 / 13 矛盾
- R10-R13：49 项承诺落实核查 / rustc 终验 / 完备性 / 启动性
- R14-R17：v1.2 残留 5 P0 + 9 rustc 错误
- R18-R20：v1.2.1 残留 3 P0 + 4 rustc 错误
- R21-R22：v1.2.2 残留 5 P0 + 决策评估
- R23：v1.2.3 最终抽样 0 P0

**版本演化**：v1.0 → v1.1 → v1.2 → v1.2.1 → v1.2.2 → v1.2.3（22 文档，0 P0）

**决策**：v1.2.3 冻结

---

### 需求 #11（2026-07-18）：编译器命名与元信息

**用户需求**：
> 我想知道你为什么取 forge 作为编译器名称，当前文档内容是否缺失有关编译器名称，文件后缀等编译器其他相关的内容文档，是否存在更合适的提名与相关内容，可通过多 agent group 团队协作思考

**AI 响应**（N1-N2 命名与元信息调研）：

- N1：37 轮调研发现 Forge 17+ 冲突 → 推荐 Quench（66/80）
- N2：发现 3 P0 + 9 P1 元信息缺失 → 新增 19-project-meta.md
- 产出 v1.3.0：Forge → Quench 重命名 + 元信息 SSOT

**决策**：v1.3.0 采用 Quench

---

### 需求 #12（2026-07-18，第 8 次）：再次审查 + 命名再思考

**用户需求**：
> 同上审查 + 并再次深入思考编译器命名与元信息

**AI 响应**（N3-N4 命名再验证）：

- N3：发现 Quench 致命冲突（QUENCH 商标 Quench.ai Ltd 多国注册 + crates.io 同名语言 + GitHub org 占用）
- N4：推荐 Fuller（29/40，锻造工具，零冲突）
- 产出 v1.3.1：Quench → Fuller 重命名

**决策**：v1.3.1 采用 Fuller

---

### 需求 #13（2026-07-18，第 9 次）：命名不必语义

**用户需求**：
> 命名或许当前为了语义放弃更好的选择，其实没必要为了语义或者其他的限制而放弃更好；就如 rust, zig, java, lua等语言它们的名称其实本身并不是通过语义的关联来选择的

**AI 响应**（N5-N6 非语义命名调研）：

- N5：调研 15 门成功语言命名模式，发现无一采用语义链命名
- N5：推荐 Landin（Peter Landin，38/50，PL 学术人名，零冲突）
- N6：v1.3.1 元信息核查发现 4 P0
- 产出 v1.3.2：Fuller → Landin 重命名 + 元信息修复

**决策**：v1.3.2 采用 Landin

---

### 需求 #14（2026-07-18，第 10 次）：命名不必人名

**用户需求**：
> 并不需要为了致敬使用人名

**AI 响应**（N7 纯粹命名探索）：

- N7 Agent 超时，主 Agent 基于前 7 轮调研积累做最终决策
- 维持 Landin，但重新框架命名理由：核心优势不是"致敬人名"而是"零冲突 + 故事可独立成立"
- Tagline 更新为 "A systems language for the next 700."

**决策**：维持 Landin + 重新框架

---

### 需求 #15（2026-07-18，第 11 次）：同步性修复

**用户需求**：
> 当前文档集中存在更新同步问题，完整审查修复后，最后返回完整包

**AI 响应**（N8 同步性审查）：

- N8：发现 29 项 P0 同步问题（19-project-meta.md 22 处 active fuller 残留 + FREEZE-REPORT 6 处过时 + README 1 处进化链不完整）
- 系统修复全部 29 P0 + 关键 P1
- 产出 v1.3.3：同步性修复

**决策**：v1.3.3 冻结

### 需求 #16（2026-07-18，当前）：Agent 团队管理文档集

**用户需求**：
> 将我给你的需求，整理为文档（每次需求的变动以及回应都需要阅读文档或者更新），同时新增项目管理 agent, 项目阶段任务细分排期agent 及 审查 agent 和记录 agent 与开发 agent，测试 agent, 架构 agent, 算法 agent, 相关 agent 的 skill 编写和管理优化 agent等, 每一个类别都至少存在 2~3个agent 成员。agent 团队成员之间协作推进项目和项目决策和风险评估等。将上述整理为项目团队 Agent Group 成员管理和协作文档集合

## 4. 需求变更管理流程

每次用户提出新需求时：

1. **阅读本文档**：了解当前项目状态与历史决策
2. **追加需求记录**：在 §1 时间线末尾添加新需求条目
3. **更新版本记录**：在 §2 版本演化表添加新版本
4. **响应需求**：按需求类型分派给相应 Agent Group
5. **记录响应**：在需求条目下添加 AI 响应摘要
